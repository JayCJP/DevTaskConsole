# 看板缓存策略方案（`GET /api/v1/board/stories`）

> 状态：review 后定稿。策略：**只做文件缓存，不做内存缓存**。
> 参考实现：`apps/server/src/aggregator/snapshot-cache.ts`（`SnapshotCache`）与其测试/夹具、以及 `docs/快照缓存重构方案.md` §3。

---

## 0. 结论与 review 要点

根因不是缓存失效，而是该接口**全程无缓存**：`server.ts:430` 路由每次都同步执行 `buildBoard()`，后者串行发起十几次 TAPD MCP 调用（`tapd.listOwnedStories` → `fetchParents` → `attachBoardBugs` 按 100 分批），耗时 1 分多钟。已有的 `enrichmentCache`(60s) 只服务 `aggregate()` 链路，看板绕过；`createSingleFlight` 只去重在建请求，不缓存数据。

**方案：把整个 `BoardResponse` 按 `owner + includeReleased` 缓存到磁盘文件，命中则零 MCP 调用。** 不引入内存缓存层。

review 时发现若直接把"纯内存 Map"改成文件，有几个必须处理的点（本方案已逐条解决）：

| # | 坑 | 修正 |
|---|---|---|
| R1 | 文件只能整体覆盖，多个 owner/includeReleased 不能各占一个文件又互不干扰 | 单文件内用 `Record<cacheKey, entry>` 存多 key，整体读整体写，沿用 `SnapshotCache` 的串行写 + 原子 rename |
| R2 | 缓存文件结构不能用 `boardResponseSchema` 校验（外层多了 version/key/fetchedAt，且 board 的 `fetchedAt` 可为 null） | 新建独立的 `boardCacheSchema`，内部 `response` 字段复用 `boardResponseSchema`，而不是手写重复字段 |
| R3 | 命中缓存时 `fetchedAt` 是上次抓取时间，前端 `useBoardStories.load()` 会把它当本次时间展示 | 保持 `fetchedAt` 真实含义（数据抓取时间），这恰好是正确语义；不做伪造，陈旧提示可基于它与当前时间差 |
| R4 | 缓存命中时若上次结果带 `error`（本地扫描/绑定失败提示）会被一起缓存 | 仅 `ok === true` 的结果写缓存；`error` 字段可能与非致命本地错误共存，force 刷新可重建，可接受 |
| R5 | 进程重启无内存缓存，冷启动每次都要读文件——这正是本方案接受的取舍（文件读毫秒级，远胜 1 分钟回源） | 读文件同步 I/O，简单直接；无需内存层 |
| R6 | 并发写同一文件会互相覆盖 | 照搬 `SnapshotCache.serialize()` 串行队列 + 临时文件 + `rename` 原子替换 |
| R7 | 损坏缓存/版本不符/结构变更会击穿或返回脏数据 | `version` 常量 + zod 校验 + try/catch 一律当 miss，绝不阻断接口 |
| R8 | 单飞去重的 key 维度必须与文件缓存 key 一致，否则 force 与普通请求互相污染 | 回源函数入参含 `owner/includeReleased/force`，`createSingleFlight` 用 `JSON.stringify(args)` 自然区分 |

## 1. 设计

### 1.1 存储位置与文件结构

复用 `getDataDirectory()`（`security/token-store.ts:6`），与快照缓存同目录、不同文件：

```
%LOCALAPPDATA%\DevTaskConsole\board-cache.json
```

结构（单文件多 key）：

```json
{
  "version": 1,
  "entries": {
    "蔡杰鹏|0": {
      "fetchedAt": "2026-11-18T...",
      "response": {
        "owner": "蔡杰鹏",
        "fetchedAt": "2026-11-18T...",
        "ok": true,
        "includeReleased": false,
        "hiddenReleased": 3,
        "stories": [ ... ],
        "workspaces": [ ... ]
      }
    },
    "蔡杰鹏|1": { "...": "..." }
  }
}
```

- `cacheKey` = `归一化owner + '|' + (includeReleased ? '1' : '0')`。owner 先 `trim()`，空则回落 `defaultBoardOwner`（与 `buildBoard` 一致），避免空格产生多份缓存。
- 用 `|` 分隔即可：owner 不含 `|`（TAPD 处理人姓名）。若要更稳妥可 `JSON.stringify([owner, includeReleased])`，二者择一。
- `entries` 顶层 `fetchedAt` 与 `response.fetchedAt` 同值（都是数据抓取时间）；命中时校验的是顶层那个，返回的是 `response`。

### 1.2 zod schema（参考 `snapshot-cache.ts:26` 的独立 schema 原则）

```ts
// 新增 shared 导出（建议在 packages/shared/src/index.ts 追加，避免服务端手写重复结构）
export const boardCacheSchema = z.object({
  version: z.literal(BOARD_CACHE_VERSION),
  entries: z.record(z.string(), z.object({
    fetchedAt: z.string().datetime(),
    response: boardResponseSchema,   // 直接复用，不重列字段（R2）
  })),
})
export type BoardCacheFile = z.infer<typeof boardCacheSchema>
```

> `BOARD_CACHE_VERSION` 常量放在服务端 `board-cache.ts`（与 `SNAPSHOT_CACHE_VERSION` 同位置同风格），结构变更时递增。

### 1.3 `BoardCache` 类（仿 `SnapshotCache`）

新增 `apps/server/src/aggregator/board-cache.ts`：

```
class BoardCache
  - constructor(directory = getDataDirectory())   // 测试注入临时目录
  - read(key): BoardResponse | undefined
       读文件 → JSON.parse → boardCacheSchema.safeParse → 取 entries[key]?.response
       不设 TTL：文件存在且合法即命中；任何异常/不存在/损坏 → undefined
  - write(key, response): Promise<void>
       串行队列（serialize）→ 读现有文件（坏文件当空）→ 合并 entries[key]
       → 原子写临时文件 + rename（mode 0o600）
  - [private] serialize(op)                        // 与 SnapshotCache 同款串行化（R6）
```

要点：
- `read` 是同步的（`readFileSync`），因调用方在单飞临界区内使用，简单直接，与 `SnapshotCache.read` 一致。
- `write` 异步（目录 mkdir + writeFile + rename），失败只记日志、不抛给路由；缓存是加速手段不是真相源。
- 写时"读现有文件再合并"：若文件损坏，`safeParse` 失败则从空 entries 开始，不丢其他 key 之外的数据（R7）。

### 1.4 缓存有效期：不设 TTL

- **无 TTL**：只要缓存文件存在、版本/schema 合法且含对应 key，就一直命中，与抓取时间无关。
- 只有文件缺失、损坏、版本不符、schema 非法时才回源重建。
- 数据新鲜度**完全靠 `force` 穿透保证**（手动刷新按钮、写绑定操作），不靠短 TTL。
- `fetchedAt` 仍记录真实抓取时间，仅作元信息/前端陈旧提示用，不参与命中判定（R3）。

> 这是 2026-11-18 的定稿调整：原 60 秒 TTL 导致"重启服务器后第一次请求"常因缓存过期而回源 40+ 秒；取消 TTL 后重启即可秒开。

### 1.5 请求流程（路由层，`server.ts:430`）

```
GET /api/v1/board/stories?owner=...&includeReleased=0[&refresh=1]
  ├─ zod 校验参数（保持现状）
  ├─ 计算 cacheKey = `${normalizedOwner}|${includeReleased?'1':'0'}`
  ├─ 若 refresh !== '1'
  │    └─ boardCache.read(cacheKey) 命中 → 直接返回 response ✔（零 MCP）
  ├─ 未命中 / 强制刷新 → loadBoard(...)（createSingleFlight 包裹）
  │    ├─ 调 buildBoard(...)
  │    ├─ 成功且 board.ok === true → boardCache.write(cacheKey, board)（不 await 完成也可，见下）
  │    └─ 返回 board
  └─ refresh=1 时跳过读缓存，但成功后覆盖写缓存
```

关于 `await` 写盘：
- 写盘失败不应让接口失败。推荐 `boardCache.write(...).catch(logError)`，**不阻塞响应**（fire-and-forget）。
- 但要注意：单飞 `loadBoard` 返回前若写盘未开始，紧接着的并发请求可能再次 miss。由于单飞已保证同一时刻只回源一次，且写入后后续请求都会读到文件，短暂窗口可接受。若追求严谨，可在单飞内部 `await write`（写盘仅一次、毫秒级），代价是回源请求多等几毫秒——**推荐 await**，语义更简单。

### 1.6 单飞（复用 `createSingleFlight`，`server.ts:1234`）

```ts
const loadBoard = createSingleFlight(
  (owner: string, includeReleased: boolean, force: boolean) => buildBoard(owner, deps, { includeReleased })
)
```

- `force` 进参数 → 单飞 key `JSON.stringify(args)` 含 force → 强制刷新与并发普通请求不会互相复用（R8）。
- 注意 `loadBoard` 内部**不读缓存**（缓存读在路由层做，命中就根本不进单飞）；它只负责回源 + 可选写盘。

### 1.7 失效与穿透

| 场景 | 触发 | 行为 |
|---|---|---|
| 首屏 / 切换 owner / 切换 includeReleased | `useBoardStories.load()` 普通调用 | 读文件缓存，命中即返回 |
| 手动刷新按钮 | `load(force=true)` → `?refresh=1` | 跳过读，强制回源并覆盖写 |
| 保存绑定 / 解绑工作区 | `saveBinding`/`unbindWorkspace` 成功后 | 应改为 `load(true)` 强制刷新，否则刚保存的绑定被缓存挡住（与快照方案 §3.5「写操作 force」一致） |
| TAPD 回源失败（`ok=false`） | `buildBoard` 异常或通道标记 | **不写缓存**，旧缓存保留；下次请求重试 |
| 进程重启 | — | 内存无状态；首次请求读文件，命中则毫秒级（本方案核心收益） |
| 缓存文件被删除/损坏/版本不符 | 手动清理或结构升级 | 回源重建并覆盖 |

> 前端改动：仅 `useBoardStories.ts` 的 `load(force=false)` 与两处写后调用改 `load(true)`；响应结构和 `boardResponseSchema` 完全不动，前端解析零适配。

## 3. 风险与对策（review 补充）

| 风险 | 对策 |
|---|---|
| 文件缓存比内存多一次磁盘 I/O | 命中时一次 `readFileSync` + JSON.parse，毫秒级；相较 1 分钟回源可忽略 |
| 多个 key 写覆盖 | 串行队列 + 读现存文件合并 + 原子 rename（R1/R6） |
| 缓存文件无限增长 | owner 维度有限（固定几个人），`entries` 扩张可控；如需可加"只保留最近 N 个 key"或定期清，首版不做 |
| owner 改名 / 工作区根目录切换 | owner 改名 = 新 key 会回源重建；看板不依赖 `workspacesRoot`，无需防串味（与快照缓存不同） |
| 缓存期间 TAPD 数据变更看不到（无 TTL 的代价） | 手动刷新按钮、`?refresh=1`、写绑定操作均可 force 穿透重建；不刷新则一直展示缓存快照 |
| 写盘失败 | 只记日志，接口仍返回本次构建结果 |
| 结构升级导致旧缓存失效 | `BOARD_CACHE_VERSION` 递增，旧文件整体丢弃重建 |

---

## 4. 效果预期

- 普通请求：命中文件缓存后**零 MCP 调用**，从 1 分多钟降到毫秒级（一次文件读 + JSON.parse）。
- 冷启动（进程重启后首次）：读文件命中则仍毫秒级，这是纯文件方案相对纯内存的核心收益。
- 手动刷新 / 写后刷新：全量回源，保持新鲜；可通过 §1.6 的并行化后续优化进一步压缩。
- 不引入内存状态，无进程内缓存一致性问题。

## 5. 后续可选（不在本方案范围）

1. 并行化 `fetchParents` / `attachBoardBugs`，压缩"回源本身"的耗时（让手动刷新也不再 1 分钟）。
2. 基于 `fetchedAt` 做前端"数据来自 xx 秒前"的陈旧提示。
